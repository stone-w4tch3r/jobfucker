# Сбор вакансий (hh.ru, Habr Career)

Резюме/требования → проверенный поисковый пул доски. Только поиск. Fetch — нет. Банк живёт в локальной БД.

Доска фиксирована в pipeline (`service.hh` **или** `service.habr`), механика поиска у них **разная** — общий протокол ниже, специфика в разделах «Механика доски.

## Вход

- Файл резюме ИЛИ требования свободным текстом.
- Извлечь: профиль роли, ключевой стек, вторичный стек, грейд, посторонние навыки/ключевые слова для жёсткого исключения.

## Спроси пользователя СНАЧАЛА

1. **Ширина** — узкий/точный против широкого покрытия. Покажи компромисс в цифрах (шум против пропущенного).
2. **Свежесть** — окно возраста вакансии (по умолчанию 30; 60/90 для бэкфилла) и только новые или старые тоже.
3. **Объём** — целевой размер банка. Регулируется шириной + окном.

Никогда не пропускай. Эти параметры принадлежат пользователю.

## Построй пул запросов

- 5-10 поисков. Каждый: строка запроса + собственный блок фильтров + обоснование.
- Ключевые слова: слова роли, слова стека, варианты написания (общие: eng + рус; HH вдобавок транслит — у Habr транслитерации **нет**, см. механику).
- Точные наборы: ядро стека + суженные комбинации + наборы «взять всё» по редким нишам.
- Наборы по локации, например remote/hybrid + крупные города + релокация.
- **Сужай структурными фильтрами, а не только словами.** Дополнительные слова в query сужают по-разному: у hh.ru работают группировки `(...)`/операторы, но кавычки и дефисные термины ослабляются; у Habr `q` объединяет слова по OR и **вообще не сужает** — только расширяет. Детали — в разделах механики.

## Протокол проверки (обязательный, ловит мусор)

1. Запусти поиск. **Счёт**: слишком много или слишком мало = плохой запрос.
2. **Проверка заголовков топ 20-40 titles**. Ранжирование досок произвольно — читай реальные заголовки, не только счётчики.
3. Повторяй для каждого кандидата, пока не ок. Итерируй.

## Механика доски: hh.ru (проверенные особенности)

- **Поле поиска = ручка ширины.** `fields_to_search_in: [name]` по умолчанию (узко). Широкий вариант: `[name, description]` — заголовок + тело. Поиск только по заголовку точен, но **пропускает вакансии с generic-заголовками** ("Разработчик", "Программист" — стек только в теле). Generic-заголовки реальны и часты. Поиск также по телам ловит их, но шум сильно растёт (любое объявление с ключевиком), дупликация растёт, стоимость проверки скачет. Гибрид: точные наборы только по имени для ядра + один набор по описанию, чтобы выметать generic-заголовки.
- **Группировка AND/OR**: `(A OR B) (C OR D)` = комбо стек × область (например `.NET` × `AI`). Group-AND работает.
- **Особенность региона**: фильтр area ВСЕГДА включает REMOTE. Набор регионов ⊇ набор remote. Пересечение ожидаемо, fetch уберёт дубли позже.
- **Сортировка**: `relevance` ≈ `publication_time` для OR-запросов по имени (идентичная доля мусора). Используй `publication_time`: детерминированно, свежее — первым.
- `exclude_words`: блокируй мусор, не относящийся к профилю поиска, например junior/intern/стажер при поиске сеньорских позиций.
- Фразы в кавычках ненадёжны — hh их дробит/ослабляет.

### Мусорные ловушки hh.ru (измеренные)

ПРИМЕР! для поиска AI-связанных вакансий. По аналогии отсекай проблемные поиски.

- `Agentic` → стемминг к `агент` → ~1100 вакансий в недвижимости. Мёртвый термин.
- `"AI-агент"`/термины с дефисом → распадаются на `AI` + `агент` (через OR) → тот же мусор из недвижимости.
- `нейросет` → 200+ мусора «обучение нейросетей» (юрист/SMM/маркетолог). Мёртвый термин.
- голый `агент` → недвижимость. Мёртвый термин.
- `copilot OR chatgpt OR gigachat OR yandexgpt` → 5 результатов, мусор. Мёртвый термин.
- `dotnet`/`Blazor`/`".NET Core"` → стемминг к `.NET`, маргинально +1. Пропусти.
- Multi-agent заголовки уже ловятся через термины `LLM`/`RAG` — отдельный поиск по агентам не нужен.

## Механика доски: Habr Career (проверенные особенности)

Замерено 2026-09-30 (baseline всей активной выдачи ≈1115). Счётчики дрейфуют ~1–2% между прогонами: см **порядок величины**, не константу.

### Синтаксис `q`

- **Разделитель по умолчанию — OR (объединение), не AND.** `php` 26 + `vue` 14 → `php vue` 35; `python` 425 + `java` 432 → `python java` 595 (> каждого). Лишнее слово в `q` только **расширяет** выдачу. Сужай фильтрами (`skills`, `qualification`), не словами.
- **Булевых операторов нет.** `OR`/`AND`/`NOT` игнорируются (`python OR django` = `python`); `python NOT java` ≈ `python java` (java добавляется по OR, не исключается).
- **Кавычки, запятая, `|`, ведущий `!`/`+`/`-` → 0 результатов молча** (не ошибка): `"python developer"`=0, `python,developer`=0, `-python`=0, `python|django`=0. `-word` **не в начале** просто отбрасывается (не исключение): `python -java` = 425 = `python`.
- Регистр не важен (`python`≡`Python`). **Кириллица и латиница — разные алфавиты**: `1c` (лат.) = 52, `1С` (кир.) = 66 — часть пула теряется; **транслитерации нет** (`питон`=0, `python`=425).
- **Матчинг стем-подобный, не подстрока**: `develop`≡`developer`≡`development`=60; `java` ловит `javascript`; `script` ловит `javascript`/`typescript`; но `ava`/`thon`/`develo` = 0. Русская морфология работает (`разработчик`≡`разработчика`=386; стем `разработк`≈655).
- **`q` — полнотекст (заголовок + скиллы + компания + тело), поля не выбираются.** `name:python` = 0. Тело реально ищется: `опыт` 842, `дмс` 346, контроль `абракадабра` 0.
- **Дефисные/слэш-компаунды ненадёжны.** Работают как единый токен: `c++` 29, `c#` 27, `.net` 104, `ci/cd` 103, `ai-агент` 20. Ломаются: `front-end`=2 vs `frontend`=32, `python/django`=0. Пиши слитный токен (`frontend`).
- Пустой/отсутствующий `q` = вся активная выдача.

### Фильтры (всё AND)

Записи пула пишутся контрактными именами `searches[].filter` (в скобках — wire-имя параметра для сверки с `docs/habr/api/search.md`); библиотека сама кодирует их в wire.

- Все фильтры и `q` пересекаются (AND); любой добавленный фильтр только **сужает**.
- **Несколько `skills` (wire `skills[]`) = пересечение (AND)**, не объединение: `446` 143 → `446+1075` 4. Id — из `docs/habr/aux/skills.yaml`.
- `qualification` (wire `qid`): градации `intern/junior/middle/senior/lead` → `1/3/4/5/6`; `2` в доске не используется (не «любой») и в контракте отсутствует.
- `sort` меняет **только порядок**, не набор (`relevance`/`date`/`salary_desc`/`salary_asc` → одинаковый счёт); неизвестное значение молча падает в relevance.
- **Ловушка `salary_from`/`salary_currency`** (wire `salary`/`currency`): без `with_salary` учитывается **предсказанная** зарплата (`salary=200000 RUR` = 698 при 165 вакансиях с указанной). Всегда пару с `with_salary: true` (тогда 85). Валюта должна совпадать с пулом: `USD` = 0.
- `locations` (wire `locations[]`): гранулярно — `c_678` (Москва) 554, `r_14068` (Москва+обл.) 557, `ct_444` (Россия) 751. Голый числовой id игнорируется — только префиксы `c_`/`r_`/`ct_` (id — из `docs/habr/aux/locations.yaml`).
- `remote: true` 377; `with_salary: true` 165; `employment` (`full_time`/`part_time`) 631/23.
- `company_ids[]`/`divisions` — не использовать: врут (0 или 500), в контракте отсутствуют.

### Тип выдачи

- `search_type: all` — **основная поверхность для банка.** Работает анонимно; `q` и все фильтры действуют.
- `search_type: suitable` — фиксированный список «подходящих» под резюме, нужна авторизация. **Игнорирует `q` и все фильтры:** `q=php`, `q=zzz-no-such`, `qualification`, `skills`, `remote` возвращают один и тот же набор (у dev-аккаунта = 121, порядок тот же). Для параметризованного поиска не годится — не проектируй `suitable`-запись с `query`/`filter` в расчёте на сужение, они молча инертны. Анонимно бессмысленна (944 — ни 1115 пула, ни 121 «подходящих»).
- Геометрия: страница ≤50 (`all`) / фиксированные 25 (`suitable`, `per_page` игнорируется), доступно ~1000 позиций, за пределами — пустой `200`.

### Мусорные ловушки Habr Career (измеренные)

- **Мёртвые термины**: `python3`, `flask`, `cplusplus`, `csharp`, `питон` = 0; `django` = **5** (Django-вакансии титулуются «Python-разработчик», django только в теле/скиллах), `front-end` = 2 vs `frontend` = 32.
- **`java` = 432, но выдачу заполняют QA-автоматизаторы** («Automation QA (Java)», «SDET (Java/Selenium)») — шумный прокси для backend-Java.
- **Ранжирование не семантическое**: `kubernetes` = 368, но первыми идут Java backend/SRE. Читай заголовки.
- **`q=python` тянет не-IT мусор по телу**: «Юрист обучения нейросетей», «Врач обучения нейросетей» (их описания упоминают Python).
- **`skills` (Python, id 446; wire `skills[]`) один слишком широк**: 143, включая «Дата инженер (ученик)», «Администратор ОС Linux», DLP — тег скилла шире роли.
- **`программист` = 32** (титулы предпочитают `разработчик` = 386, стем `разработк` ≈655).
- **Обще-телесные кириллические слова бесполезны**: `опыт` 842, `требования` 473, `условия` 351 ≈ «всё, где есть описание».
- `1c` (лат. 52) ≠ `1С` (кир. 66) — выбирай алфавит под цель или бери оба.

### Рычаги объёма Habr (по возрастанию шума)

`qualification` → `skills` (AND точных id) → `with_salary` → `locations` → `remote` → один широкий `q`-слово → несколько `q`-слов (OR) → широкий тег скилла → телесные кириллические `q`-слова.

## Математика объёма (реши, потом скажи пользователю)

- Суженные комбо часто **строгие подмножества** ядровых наборов → дают 0 уникальных. Проверь перед обещанием объёма (hh: fullstack∧.NET ⊆ .NET ядро 27 ⊂ 234; habr: `q`+`skills` всегда ⊆ `q`).
- Докладывай реальный размер рынка честно. Если цель недостижима без шума — так и скажи.
- Рычаги роста — по доске (см. раздел механики: у hh это `within_days` → термины → name→name+description → убрать exclude_words).
- Сырая сумма ≠ уникальные: наборы регионов ⊇ наборы remote, подмножества схлопываются. Оцени уникальные после дедупликации.

## Инкрементальный режим (расширение существующего банка)

- **Обновление нового**: перезапусти те же поиски на скользящем окне → всплывают свежие вакансии. Fetch идемпотентен (дедуп по external_id). Повторный поиск = безопасное превью.
- **Бэкфилл старого**: пул исчерпан → расширь `within_days` на тех же запросах (или старый диапазон from/to).
- Проверь статус БД в выводе поиска (new vs fetched/scored/applied), чтобы увидеть реальный дефицит.

## Выходной артефакт

- Сохрани ВСЕ проверенные наборы как записи `service.<board>.searches[]` в pipeline YAML (конвенция: `pipelines/pipeline.*.yaml` в этом репо). Один профиль = один файл.
- Каждая запись самодостаточна: её `query` + её собственный блок `filter` (+ опциональный `window`). У Habr запись также несёт `search_type`.
- Новый pipeline: `jobfucker init --config <file>`. Существующий pipeline: отредактируй пул, затем `jobfucker update --config <file>`.
- Храни измеренные счётчики, даты, ловушки, обоснование как YAML-комментарии рядом с записями.
- Проверь, что YAML парсится после правки; перепроверь набор, вставив его query/filter в `jobfucker search --pipeline-id <id> --query '<q>' --params <file> --format json`. (`--params` — это `searches[].filter`; у Habr `search_type` задаётся в записи пула, не в filter.)

## Гейты качества — готово только когда

- Каждый набор проверен по заголовкам и чист.
- Счётчики записаны с датой.
- Ловушки отсутствуют.
- YAML валиден и pipeline сохранён через `init`/`update`.
- Fetch не выполнялся (только поиск/превью, на уровне листинга).

## Продолжение

- `jobfucker fetch --pipeline-id <id>` проходит по каждой записи `searches[]` в БД. Только по явной просьбе/одобрению пользователя.

## Где искать команды

Синтаксис CLI, обнаружение pipeline-id, флаги `search` меняются со временем. Читай их в AGENTS.md проекта / `app search --help`. Каталоги id для Habr — `docs/habr/aux/`.
