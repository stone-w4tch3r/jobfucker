1Executive verdict

The core is real and coherent. The mock-driven pipeline (config → snapshots → fetch/score/generate/apply → SQLite, Result-style errors, audit log, daily limits) is implemented, typed, and tested. The HH client is further along than any doc admits: browserless login + OAuth + token persistence + both captcha protocols + sliced search with detail enrichment all exist and are BDD-tested against a mock transport. Only resume listing and applying are explicit fail-closed stubs.
The docs match the code. AGENTS.md carries the truthful status table and the full command list; the architecture spec is a compact as-built that declares the ORM the schema authority; the product spec documents behavior and marks unsettled semantics (limits, vacancies filter) as explicit TBD. Remaining doc-code gaps live in the matrix in §17.
The "impossible to understand" feeling has a structural cause. 20% of source lines are docstrings (many are 30–50-line essays); generic three-type-parameter frameworks wrap single concrete uses; the same concern is restated in module docstrings that duplicate spec-level facts — docs declare single fact-homes and link, but the docstring essays remain. Complexity inventory in §19.

2Mental model — how one command actually flows

The single most useful thing to know: the DB is the config. After init, no command reads pipeline.yaml again; every stage run reconstructs a full PipelineConfig from the stored snapshot row ("we trust the db", zero file I/O). The second most useful thing: everything below the CLI is async and returns Result — exceptions are programming errors only.

Pseudocode — the five invariants that explain most code you'll read
# 1. Errors are values. Every boundary returns Result[T, E]; unwrap_err paths are the error handling.
async def stage(...) -> Result[Report, str]:        # whole-batch Err (auth/transport/plan)
    ...                                            # per-item failures are FIELDS on rows, never aborts

# 2. Config lives in the DB, snapshot per real change, reconstructed with zero file I/O.
snapshot = storage.snapshots.current(pipeline_id)
config   = reconstruct_pipeline_config(to_persisted_refs(snapshot))   # login/password/resume/api_key/prompts are CONTENT columns

# 3. Provenance: every artifact column records which snapshot produced it.
vacancy.scored_snapshot_id = engine.snapshot_id   # + fetched/generated/applied_snapshot_id

# 4. Fetch is an insert-only mirror sync; --refresh overwrites listing fields only.
fetch:  insert new ids; existing rows untouched        # stored ids excluded client-side
score:  skip if --skip-already-processed and row has result

# 5. One shared daily counter per (service, login, date); two caps checked against that ONE value.
can_apply = used < per_auth_cap and used < per_pipeline_limit   # limits.py:53, called as can_apply(used, used)

4Data model

Five tables. The docstring of storage/models.py:4 cites docs/specs/jobfucker.pipeline-snapshots.md as the DDL authority — that file does not exist; the ORM is the only authority, as the architecture spec (§21) states explicitly.

Provenance semantics — the part worth keeping

Every artifact field records the snapshot whose config produced it: fetched/scored/generated/applied_snapshot_id. Fetch is insert-only and never resets results: existing rows keep their score/letter/apply state and provenance verbatim; --refresh overwrites listing fields only and bumps fetched_at, which is what marks the row stale (score/letter/user) until the stage re-runs (stages/fetch.py:169-209). This is the "old cfg ids stay attached to old step results" idea from the spec — implemented more rigorously than the spec describes.

5Pipeline lifecycle & config

Config loading rules (as coded)

  • service: must be a mapping with exactly ONE board key; that key is the adapter selector string. The loader takes only the mapping form; docs/examples/pipeline.example.yaml is the reference example.
  • Every content slot is exclusive-or: file reference or inline value (auth login/password, resume, api_key ×2, both prompts). Both present → Err; required slot missing → Err. Pre-checked on raw YAML before pydantic for clear messages.
  • File contents are read once at init/update, strip()ed, stored as CONTENT in the snapshot. Later runs never re-read files.
  • daily_apply_limit validated ≤ adapter's per_auth_daily_cap at init/update time (fail = Err, nothing persisted).
  • Reconstruction re-validates the opaque service_section/openai_captcha JSON through the registry; corrupt row = clear Err ("re-run init").

6Stage engine — real behaviors

Pseudocode — apply eligibility & outcome mapping (stages/apply.py)
def eligible(v, min_score):
    return not v.manual_skip                        # soft-deleted rows never reach this (list filters them)
       and v.cover_letter is not None                 # must have a letter
       and v.apply_status not in {applied, skipped, error} # idempotency
       and v.score is not None and v.score >= min_score

for vacancy in candidates:                       # ordered by... insertion (list_by_pipeline order)
    if not limits.can_apply(used, used):            # SAME value twice — one shared counter
        stop_early; break                          # remaining stay pending; Ok report w/ limit_reached
    r = client.apply_to_vacancy(resume_id, external_id, message=cover_letter)
    match r:
      Err(LimitExceededError) -> pending, stop
      Err(other)               -> apply_status=error, continue    # per-item, never abort
      Ok(ApplySucceeded)       -> applied, applied_at=now, daily_limits.increment(service, login, date)
      Ok(ApplySkipped(skip))   -> skipped
      Ok(ApplyFailed(err))     -> error
Pseudocode — fetch stage contract (stages/fetch.py)
plan = plan_fetch(params, max_search_items)        # pure validation, BEFORE any I/O
stored = repo.list_external_ids(pipeline.id)       # exclusion set for the client call

                                limit=plan.slice_end-plan.slice_start,
                                page_size=plan.page_size,
                                exclude=stored)    # stored ids skipped on the client
for vacancy in slice.items:                       # non-excluded only
    existing = repo.get_by_external_id(pipeline.id, vacancy.external_id)
    if existing is None:  insert                        # insert-only mirror sync

    elif not inputs.refresh:  skip                    # already stored; --refresh to overwrite
    elif listing unchanged:  skip                    # dirty-check: no write, no fetched_at bump

# soft_deleted_at is the only deletion and is set manually, never by fetch.

    persist-everything-loaded; return Err("failed on page X/N; pages A-B (k vacancies) persisted; re-run with --from M ...")

8Limits — what is actually tracked

Reality

ONE counter per (service, login, date) in daily_limits, shared across all pipelines on the account. Before each apply, that single count is checked against BOTH caps: adapter's per_auth_daily_cap (hh=200, mock=200) and the pipeline's daily_apply_limit. Effective stop = tighter cap. Incremented only on ApplySucceeded. Board's LimitExceededError also stops the batch (leaves rest pending, Ok report).

limits.py:53 → used < per_auth_cap and used < per_pipeline_limit
apply.py:168 → can_apply(used, used) # same value twice

Spec says

Semantics are TBD: the product spec treats the current shape as corrupted by design drift (the API models two counters; the DB and callers have one) and documents only what is verifiable — one shared count checked against both caps. No settled per-pipeline semantics exists.

OPEN: is a true per-pipeline counter wanted? Decide before relying on limits.

User note

The Limits two-counter finding — "API models two counters; DB + callers have one. Speculative generality that misleads readers." — sounds not ok; will address it later.

14Vacancy document workflow

A git-merge-style review/edit loop over the vacancy table, implemented as a generic "table documents" framework with exactly one concrete table. YAML (or JSON) doc: read-only context block (listing + staleness timestamps + computed stale flags), editable block (7 fields: score, score_reasoning, cover_letter, notes, manual_skip, manual_skip_reason, deleted), technical metadata block (primary key, provenance, per-field sha256 base hashes), schema URL + embedded editing instructions + content-hash schema version.

Audit view

Legitimate core need

Review/edit vacancies with real tools ($EDITOR, yq/jq filtering for "only score ≥ 4"), batch-select a subset for apply, manual corrections with audit trail. The workflow itself is coherent and the atomicity/conflict thinking is careful.

Overbuilt for its consumer

Concurrent-writer conflict detection for a single-user local DB; content-hash schema versioning with dual artifact copies (docs/ + packaged resource) for one document type; a generic 3-type-param framework for one policy; global cross-pipeline dump (no --pipeline-id filter!). This is the clearest "artificial feature baked into DNA" specimen: useful seed, ~5× the necessary machinery.

15Reporting & logging — two parallel output systems

  • RunEvents (reporting.py): live semantic events (stage, level, index/total, item, url, message) → CLI prints filtered by -v (success/warn/error at 0, info at -v, debug at -vv). Designed so a GUI could bind the same stream. GUI is gone; the stream still earns its keep for -v output.
  • Logging (shared/logging): always-on file log at $DATA_DIR/logs/jobfucker.log, level via --log-level (debug = full AI request/response exchange); optional colored stderr mirror; noisy third-party loggers pinned to WARNING.
  • TODO floats a third idea (intercept reporters into the log). Not implemented.
