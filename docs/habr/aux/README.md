# Auxiliary id catalogs

Generated dictionaries of Habr Career filter ids, used when writing search configs for the future
client. They are **data, not behavior** — the semantics live in [Search and listings](../api/search.md).

| File | Contents |
| --- | --- |
| [skills.yaml](skills.yaml) | `skill id → {name, alias}` (the `skills[]=` filter values) |
| [locations.yaml](locations.yaml) | `country`, Russian `region`, and Russian `city` ids, plus the in-use city subset |

> Generated by `tools/catalog/habr.py` (`uv run poe catalog_habr`). Ids belong to the board's geo
> database and are append-only; treat the files as a snapshot and refresh them periodically.
> Current size: ~470 KB (was ~1.3 MB when foreign cities were mirrored).

## Scope

The location catalog is deliberately **not** a mirror of the board's geo table (which is a worldwide
settlement list, ~100k+ rows, only reachable through a 25-result autocomplete). It keeps:

- **countries** — every country row (tiny, and `locations[]=ct_<id>` is a usable filter);
- **regions** — Russia only (`ct_444`);
- **cities** — Russia only (`ct_444`);
- **in_use_city_ids** — city ids referenced by current vacancies, restricted to the cities above.

Rationale: the vacancy filter accepts `locations[]=c_<id>` / `r_<id>` / `ct_<id>` (and
`city_id=<bare id>`), so region or country granularity already covers most search configs — a
worldwide city dump buys nothing. Measured: against a 1217-vacancy baseline, Москва → 597,
Москва и Московская область → 599, Россия → 808.

If a wider scope is ever needed (worldwide, another country, or a demand-only catalog), widen
`should_expand_locations` and the matching filters in `merge_locations`; the module docstring in
`tools/catalog/habr.py` says exactly what to change. No other code depends on the scope.

## Provenance and method

The board publishes no bulk dictionary; the only public source is the 25-result autocomplete:

```http
GET /api/frontend/suggestions/skills?term=<prefix>
GET /api/frontend/suggestions/locations?term=<prefix>
GET /api/frontend/suggestions/countries
```

A prefix trie crawl (`term=<prefix>`, expand a prefix with each next character while the response is
capped at 25 and adds new entries) recovers everything reachable. Skills are crawled to full depth;
locations are crawled **only down branches that contain a Russian entity**, so foreign branches are
never expanded. Country names come from the `ct_` rows and from city/region `subtitle` prefixes
(`"Россия, Хакасия"`), with `ct_` titles taking precedence. In-use city ids come from a listing scan
(`GET /api/frontend/vacancies?type=all&per_page=50&page=N`, `items[].locations`).

## Coverage

| Section | Count | Notes |
| --- | --- | --- |
| `skills` | 1617 | full prefix-crawl; effectively complete |
| `countries` | 200 | ids observed as `ct_<id>`; `country_slugs` holds the endpoint's 25-slug list |
| `regions` | 84 | Russian federal subjects (`r_<id>`, `country_id: 444`) |
| `cities` | 6080 | Russian cities/settlements (`c_<id>`); foreign cities are out of scope |
| `in_use_city_ids` | 39 | the practical subset for real pipelines (restricted to the cities above, so a foreign in-use city is not listed) |

Russian settlement names are enumerated to the depth the crawl budget allows; a name the crawl has
not seen yet is simply absent (the file only grows, so re-running recovers it).

## Semantics

- `cities` keys are the bare number of the `city_id` query parameter (`/vacancies?city_id=678`, i.e.
  autocomplete value `c_678`); for `locations[]` prepend `c_`.
- `regions` keys are bare numbers of `r_<id>` entities; `countries` keys are bare numbers of
  `ct_<id>` entities.
- `skills` keys are the `skills[]=<id>` values.
- Duplicate settlement names exist (e.g. two "Аршан" rows); a name alone is not a unique key — use
  the region to disambiguate.
- Ids are append-only and stable; never hard-code them in code — reference this catalog when
  authoring a pipeline config.

## Refreshing

```bash
uv run poe catalog_habr sync --kind in-use --write      # cheap (~20 requests): in_use_city_ids only
uv run poe catalog_habr sync --kind skills --write      # full skills crawl (~10 min)
uv run poe catalog_habr sync --kind locations --write   # Russian regions/cities crawl
uv run poe catalog_habr sync --kind all --check         # CI-style staleness check, exit 1 on drift
```

- Sync is **additive**: a capped crawl can miss entries, so ids are never deleted; the scope filter
  is what drops foreign entries carried by an older file.
- A throttled or budget-limited crawl is resumable with `--resume` (checkpoint in the system temp
  dir). Exit codes: `0` clean, `1` drift under `--check`, `2` error or crawl aborted.
- The crawl is anonymous and polite (single-digit concurrency, pacing) and stops on `403`/`429`.
- `--budget N` / `--concurrency N` bound a run; `--root` points at a different checkout (tests use
  that with a mocked transport — see `test/tools/catalog/`).
